# CI/CD 与验收测试设计 v0.1

本阶段先固定契约、测试目标、失败判据和运行边界，再实现连接器。
环境条件可以通过后续测试逐项关闭；单个写入阶段只要求其自身前置条件满足。
离线测试不等待设备 NTP、NETCONF、DNS、RA 或模板配置完成。

当前实现仓库检查、SDK 行为表征、HTTP 边界、只读 Provider/SQLite 及 NETCONF/SSH 合成服务器测试。`tests/catalog.json` 是用例清单；
`implemented` 表示有可执行测试，`planned` 表示验收目标仍待实现。
CI 通过不等于所有清单用例通过，也不等于已完成生产自动续期。

## 1. 流水线分层

| 层级 | 触发与运行位置 | 主要检查 | 合并或升级条件 |
|---|---|---|---|
| P0：仓库与契约 | 每个 PR、main/develop push；GitHub hosted runner | 用例目录、上游快照摘要、工作流安全约束、actionlint、Go 格式/vet/race、SDK v1 路由与 DTO、漏洞检查 | 当前阶段所有已实现检查通过；兼容差异显式记录 |
| P1：只读实现 | PR；合成 CLI/NETCONF fixture、内存 fake server | PEM/绑定解析、错误输出、每操作能力、SSH host key、AAA 拒绝、只读命令边界 | 实现发现功能前，对应失败测试先进入 PR；实机只读验收另记 |
| P2：备用槽位 | PR 离线模拟 + 手动实验环境 | 非导出密钥、CSR、签发、CA 链、导入；HTTPS 旧指纹保持 | staging 用例通过，原 HTTPS 绑定未被修改 |
| P3：切换与恢复 | PR 故障注入 + 手动维护窗口 | 独立 TLS、切换超时、回滚、持久化冲突、进程崩溃恢复 | 新证书生效、旧证书可恢复；保存失败不得标记 COMMITTED |
| P4：调度与交付 | PR 模拟时钟；受保护 release 流程 | ACME 订单恢复、续期抖动/退避、重启、SBOM、镜像扫描与签名 | 功能门槛和 release 门槛全部满足，才允许发布预览包 |

目前启用 P0 与 P1 中的离线 HTTP 边界、Entity 持久化及只读 Provider 检查，
详见 [边界实现](provider-boundary.md) 和 [只读 Provider](readonly-provider.md)。
设备库存语义解析、真实设备验收及后续写入阶段仍为验收设计，不以空实现、`skip` 或始终成功的 mock 代替。
发布镜像与设备部署分别设门槛。

## 2. 已启用的 P0

- 固定 ILM `interfaces` **2.19.0** commit 和 Java 源文件 SHA-256。
- 固定 Go SDK **v1.1.0**。检查 Provider 报告的路由是否覆盖已核对的 2.19.0 子集，
  并通过 SDK 的真实 HTTP handler 调用测试替身。
- 比较 SDK DTO 可序列化字段和 2.19.0 Java 字段；验证 CSR/push 关联载荷、
  `withKey`、`multipleEntries`、`supportKeyManagement` 等字段的线格式。
- 表征 SDK 的 Info、Health、错误格式及输入解码行为；不假定 v2 默认适用于 v1。
- 显式记录属性校验成功码差异，见 [兼容说明](compatibility.md)。
  这部分通过意味着“差异仍被看见”，不表示差异已修复。
- 两条 Go 版本线分别执行 race 测试；漏洞扫描涵盖测试代码依赖。
- 工作流仅使用 read 权限、完整 SHA 的 Actions 引用和 hosted runner。

不把 SDK 示例中的占位 CSR 或证书当成有效签发证据。本阶段测试中的短字符串
只验证字段编码；真正的 X.509/CSR 语义验证属于 P2，并用运行时生成的密钥。

## 3. 后续验收集合

详细 Given / When / Then 断言以 `tests/catalog.json` 为准，按以下风险组织。

| 集合 | 核心验收 | 必须出现的负向情形 |
|---|---|---|
| 发现与能力 | 证书内容、活动绑定、备用与回滚角色分别识别；只报告已测试能力 | 多证书、损坏 PEM、截断输出、未授权、缺少 YANG 节点、未知版本、只读端出现配置命令 |
| 连接安全 | SSH host key 固定、HTTPS CA/名称校验、最小权限 | 主机密钥变更、错误 CA/主机名、AAA 拒绝、连接到未批准地址、日志泄漏 |
| CSR 与签发 | 设备内新密钥、CSR 验签、SAN/EKU/用途与实际模板策略一致 | 已用槽位、错误密钥、非预期 SAN、错误模板、待审批、签发超时、重复调用 |
| 导入与切换 | 先 STAGED，后受控切换，新连接验证预期叶指纹与链 | 证书/CSR 公钥不匹配、未知根、已过期/尚未生效、错误服务、TLS 缓存连接 |
| 回滚与恢复 | 原绑定与旧 TLS 均验证后才报回滚成功 | 切换成功但应答丢失、切换后崩溃、回滚失败、保存失败、其他管理员同时修改 |
| 幂等与并发 | 一个 Location 一个续期责任方；API/worker 共用锁 | 双 worker、Core 与 worker 冲突、重复 push、旧 operation ID、跨设备重放、磁盘失败 |
| ACME | 使用外部 CSR，恢复原订单，按服务端支持完成挑战 | badNonce、429/Retry-After、账户密钥缺失、DNS 清理误删、到期窗口与时钟漂移 |

关键断言须检查**副作用数量与禁止发生的副作用**，不仅检查返回码。例如：
签发超时后恢复同一订单，不能再创建第二个订单；stage-only 模式下任何路径均
不得调用 HTTPS 绑定写入；回滚保存失败不能返回 ROLLED_BACK。

## 4. 测试替身与故障注入

先使用窄接口：Device、Issuer、DNS、Journal、Clock、TLSProbe。替身记录每个
读写意图与调用次数，可以在副作用前、执行成功但应答前、日志落盘后、进程
恢复时注入故障。设备替身必须能表达 running/startup 配置、证书存储和 HTTPS
实际呈现状态彼此不一致，不能让一个变量同时代表全部状态。

CSR/证书测试在运行时生成测试 CA、叶密钥、SAN/EKU/期限组合。需要确定性时
固定测试时钟和证书字段，不在仓库保存私钥。PEM、NETCONF XML 与 CLI 文本使用
合成 fixture，包含换行、提示符、分页、错误码和格式差异。录制真实输出只能先
放到私有环境，脱敏并人工确认后才能成为公开 fixture。

持久化测试使用临时数据库：重启读回、锁争用、未完成操作对账、唯一操作标识、
磁盘不可写/满、WAL 恢复。模拟协议成功不能代替 SQLite 的实际落盘测试。

## 5. 实机测试的三个独立入口

本仓库目前**没有**可以接入实机的工作流。先在受控管理网络手动运行测试，
默认只读；后续如需 Actions，采用独立私有实验仓库中的一次性 runner。
公网仓库不注册可进入管理网的 self-hosted runner，也不接收设备凭据。

| 入口 | 单次试验前置条件 | 可做的动作 | 必须留存的私有证据 |
|---|---|---|---|
| `read-only` | 目标地址/SSH host key、获准账号（可有读写权限）、允许的来源、明确 CLI 或 NETCONF 范围 | 固定只读操作：版本、能力、证书、绑定、时间；不自动启用协议 | 版本、实际权限、证书与绑定、重复 TLS、命令审计；仅所选 NETCONF 路径要求模型 revision |
| `stage-only` | 只读已通过、时间同步、独立恢复会话、备用名称不占用、RA/模板与链核实、挑战权限可用 | 新备用密钥与 CSR；签发并导入备用 Trustpoint | CSR/证书公钥一致、SAN/EKU/模板、备用状态、生产旧 TLS 指纹保持 |
| `activate` | staging 已通过、批准的目标与操作 ID、维护窗口、旧槽位/密钥保留、独立 TLS 探测与恢复可用、无配置冲突 | 切换、TLS 验证、持久化或恢复 | 前后指纹、服务可达性、运行/启动配置结果、回滚实测与最终状态 |

#6 的只读验收允许使用获准的读写账号，以固定操作清单及前后证书/绑定
核验界定行为。NTP 按操作者决定移到下一次实机测试 #15 / L-002 补齐，
仍在后续实机签发/staging 前核实；CLI-only 通过不表示 NETCONF 模型已验证。
原始实测报告不可改写；范围调整使用包含原报告摘要的独立评估文件。

后续实验工作流只能手动触发，消费审阅过的 main 上完整 commit SHA，重新
验证该 commit 的 CI 结果和 artifact 摘要。read-only、stage-only、activate
使用不同审批环境与最小权限凭据；环境配置本身也要核验，不能假定 YAML 中
写了 environment 就已启用审批。禁止 PR 代码、PR artifact 或参数字符串
直接成为管理网命令。真实日志保留在私有存储，公网只报告脱敏结果摘要。

## 6. CD 设计与版本策略

业务代码形成可运行程序后，再添加手动的预览 release 流程：完整 commit 已通过
CI → 构建固定依赖/基础镜像的 Linux 产物 → 单元/协议模拟集成测试 → SBOM →
依赖与镜像漏洞扫描 → 生成摘要与构建来源证明 → 受保护 release 环境批准 →
发布不可变版本 tag 和摘要。首次产物标记 pre-release，不声明生产兼容。

release job 与 PR job 分离。只有发布 job 获得最小的 packages/write 或
attestation/OIDC 权限。通过标签名称本身不能授予发布权；必须校验 commit 在
main 历史中、对应 CI 已通过，且没有未解决的发布阻断项。扫描失败、报告缺失或
前置测试未运行均不得发布。发布镜像不会自动触发设备激活。

## 7. 完成判定

每个里程碑的 PR 附用例 ID、失败测试与修复后的结果、执行版本、未覆盖项。
对 P2/P3，增加私有证据引用，公网不能附真实设备日志。所有高风险用例先于
对应写功能实现并通过；任何状态为 planned 的发布必需用例均阻断相应阶段。

首个实现 PR 应解决已发现的 v1 契约差异并完成只读 provider/解析器的失败测试，
不等待所有环境条件关闭。之后才进入备用 Trustpoint 的 CSR 与导入。
